## Findings

### P1 — The candidate pipeline never creates or verifies the deployed deliverable

**Evidence:** `.github/workflows/ci.yml:35-45`, `playwright.config.ts:3-35`

The workflow installs dependencies, runs local verification, starts Playwright's local API/Vite servers, and builds two local container images. It does not publish immutable artifacts, deploy a preview, pass a preview URL to Playwright, capture evidence from that preview, promote the exact accepted image to staging, or run a staging smoke test. Because `E2E_BASE_URL` is unset in the workflow, Playwright explicitly falls back to `127.0.0.1` and starts local services.

This omits the primary vertical outcome of Sprint 00 and leaves the delivery path untested. A green workflow can therefore coexist with a completely undeployable candidate.

**Required resolution:** add a provider-backed candidate pipeline that publishes content-addressed web/API artifacts, deploys an immutable per-story preview, runs Playwright with that preview's `E2E_BASE_URL`, runs evidence capture against the same build identifier, and publishes deployment/test inputs. After both reviews, promote those same artifact digests to staging and run the heartbeat smoke test without rebuilding from an unpinned branch.

### P2 — The required retry/recovery behavior is not exercised

**Evidence:** `apps/web/src/App.test.tsx:44-58`, `tests/e2e/system-heartbeat.spec.ts:3-23`, `scripts/capture-story-evidence.mjs:93-111`

The failure component test proves that a retry button is rendered, but it never clicks the button or changes the mocked API from failure to success. The E2E test covers only the healthy path. The evidence script creates an unavailable screenshot but likewise never activates the retry action. A broken `onRetry` handler or a retry that repeats stale failure state would pass every current check.

This falls short of acceptance criterion 3 and the contract's requirement that E2E cover the story's most important failure/recovery path.

**Required resolution:** make the component test fail the first request pair, click `Try again`, return valid responses on the next pair, and assert the state reaches `System online`. Add the equivalent deployed E2E recovery scenario by failing the first heartbeat request, removing the failure condition, clicking retry, and observing the online state.

### P2 — Evidence capture can recursively delete an arbitrary configured directory

**Evidence:** `scripts/capture-story-evidence.mjs:8-22`

`EVIDENCE_DIR` is resolved without a scope check and then passed directly to recursive `rm`. A typo such as `EVIDENCE_DIR=story`, `EVIDENCE_DIR=.`, or an absolute path can delete authoritative story records or other workspace/user data before the browser is launched. This risk is disproportionate to a capture helper.

**Required resolution:** reject every output path except a validated directory beneath the intended `story/00-system-heartbeat/evidence` boundary, explicitly reject the workspace root and ancestors, and preferably capture into a newly created temporary sibling directory before atomically replacing only the validated evidence directory after successful capture.

### P2 — Sprint 00 CI omits required static supply-chain/security gates

**Evidence:** `.github/workflows/ci.yml:35-45`, `package.json:19-28`, `eslint.config.js`

The configured static/build path covers formatting, code linting, and types, but it has no secret scan, dependency vulnerability check, license policy check, or container vulnerability scan. The newly added `scripts/` directory is also outside the ESLint command, so the evidence generator is not included in JavaScript linting. These checks are explicitly part of the contract's static/candidate pipeline and are especially important before publishing containers or accepting model/audio dependencies in later stories.

**Required resolution:** add reproducible, blocking secret, dependency, license, and built-container vulnerability checks with documented allowlists for intentional exceptions. Include `scripts/` in ESLint. Pin scanner/action versions sufficiently for reviewable CI behavior.

## Non-blocking observations

### P3 — Duplicate Ruff execution adds noise without coverage

**Evidence:** `.github/workflows/ci.yml:37-38`, `package.json:20-21`

`npm run verify` already invokes `npm run lint`, which invokes the same Ruff command executed again by the next workflow step. Remove the duplicate or give the separate step a distinct purpose/report.

### P3 — Raw parser/transport errors are rendered as user-facing diagnostics

**Evidence:** `apps/web/src/api/system.ts:13-30`, `apps/web/src/hooks/useSystemSnapshot.ts:27-36`, `apps/web/src/components/SystemStatus.tsx:42-45`

Displaying `Error.message` directly can expose verbose Zod internals and provides inconsistent user copy. Keep detailed diagnostics in a controlled development/telemetry path and map expected network, HTTP, and invalid-contract failures to concise actionable messages.
