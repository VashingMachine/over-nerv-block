### P3 — responsiveness and real-worker cancellation E2E remain masked by visible dwell

The production component intentionally keeps analysis visible for at least 500 ms and applies that delay after the worker promise has already resolved (`apps/web/src/localAudio/LocalAudioPicker.tsx:175-184,403-408`). The production E2E heartbeat counts ticks until the final result, and the cancellation journey clicks as soon as the progress UI is visible (`tests/e2e/local-audio.spec.ts:113-137,174-180,249-273`). A fast worker can therefore finish before either assertion while the UI is still satisfying the dwell.

Static worker construction, cooperative stage yields, adapter cancellation, listener cleanup, and component stale-result suppression are independently covered, so this does not block acceptance. A later hardening test should measure maximum heartbeat gaps only between actual worker progress messages and cancel a deterministically in-flight long-running worker.

### P3 — runtime worker-error validation is broader than the wire protocol

The typed worker can emit baseline analyzer error codes or `analysis_failed` (`apps/web/src/analysis/beatAnalysisProtocol.ts:29-30`), but runtime validation accepts any key in the combined boundary-message map, including main-thread-only codes such as `missing_samples`, `analysis_too_large`, and `worker_unavailable` (`workerBeatAnalyzer.ts:16-38,223-238`). The in-repo typed worker cannot emit those values, and any accepted error still settles and cleans up, so the impact is limited to boundary exactness. A dedicated runtime `BeatAnalysisWorkerErrorCode` whitelist and a negative main-only-code test would remove the mismatch.
